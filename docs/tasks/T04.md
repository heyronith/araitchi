# Task 4 — Council engine

Repo: `heyronith/araitchi` (Task 3 done at `abda7ef`). Read `AGENTS.md`, `docs/STATUS.md`, `docs/ARCHITECTURE.md` first. Save these instructions as `docs/tasks/T04.md`.

**Scope:** a user can send one message to a **council of 3–10 models** that answer independently, then a synthesizer produces a final answer plus a structured **disagreement analysis**. **Out of scope:** automatic routing (Auto stays disabled until Task 7), tools/web/papers (Task 5), task-specific merge modes (Task 7).

## 0. Housekeeping

## 1. Council configuration (per project)
- Store in the project's `notebook.db` (new `project_settings` key/value table): `council.members` (3–10 model ids, ordered), `council.synthesizer` (model id), `council.maxOutputTokensPerMember` (default 2000), `council.budgetCapUsd` (default 0.50 per request), `council.memberTimeoutSec` (default 120), `chat.mode` (`solo|council`).
- **Presets resolved from the live model catalog** (never hard-code model ids that might disappear): `Balanced` = the strongest general model from each of 3 different major labs; `Budget` = 3 strong open-weight models from 3 different labs (cheapest that support ≥ 64k context); `Custom`. Define "strongest" with a simple documented heuristic over the catalog (e.g. price tier + context + reasoning support) and let the user edit the result.
- Validation: 3–10 members, no duplicates; **warn** (don't block) if fewer than 3 distinct labs.

## 2. Council pipeline (server)
- `POST /api/council/estimate` → estimated cost range for the next message: input ≈ chars/4 of the full context per member × input price + `maxOutputTokensPerMember` × output price, for every member + the synthesizer step. Return per-member and total.
- `POST /api/chat` accepts `mode: "solo" | "council"` (keep one endpoint; origin guard; zod). In council mode:
  1. **Budget check:** if the estimate's upper bound > `budgetCapUsd`, reject with a clear error unless the request carries `allowOverBudget: true` (user confirmed in UI).
  2. **Members in parallel, independently:** each gets the same context (project brief + pinned records + chat history of the active branch) plus a member system prompt (in `src/lib/server/prompts/council-member.md`): *"You are one of several independent researchers. Answer fully on your own. State assumptions and uncertainty. Cite sources (title/DOI/URL) when you rely on them; never invent citations."* Members never see each other's answers.
  3. **Resilience:** per-member timeout; on error retry once; then, if configured, substitute a fallback model from a lab not already in the council (mark it `substituted`). Continue if ≥ 2 members succeed; otherwise fail the council with a clear error (keep partial outputs).
  4. **Synthesis:** send the member answers **anonymized** (Member A, B, C…, order shuffled) to the synthesizer with `src/lib/server/prompts/council-synthesizer.md`. It must return JSON validated by zod:
     ```
     { finalAnswer: string (markdown),
       consensus: string[],
       contradictions: { topic: string, positions: { member: string, stance: string }[], needsEvidence: boolean }[],
       uniqueInsights: { member: string, insight: string }[],
       blindSpots: string[],
       confidence: "low" | "medium" | "high" }
     ```
     Rules in the prompt: **never settle a factual disagreement by majority** — list it as a contradiction with `needsEvidence: true`; keep genuinely different ideas distinct instead of averaging them. Use structured outputs when the model supports them; otherwise JSON mode with one repair retry. Map members back to model ids after parsing.
  5. **Streaming:** use the AI SDK UI message stream with typed custom data parts: `data-member` (start / text delta / finish / error / substituted, with model id, usage, cost, latency), `data-synthesis` (text delta of finalAnswer if streaming is possible, otherwise final), `data-analysis` (the parsed object), `data-council-summary` (members ok/failed, total cost, total time).
  6. **Stop** aborts all member and synthesizer requests.
- Usage/cost for every call (members + synthesizer), summed.

## 3. Persistence
A council reply is one assistant message whose parts hold: each member (model, content, status, usage, cost, latency, substitutedFrom), the analysis object, the final answer, totals. Retry regenerates the whole council as a new branch. Session transcript export (`sessions/*.md`) includes the final answer, a compact disagreement summary and each member's answer under headings.

## 4. UI
- **Mode switch** in the top bar: `Solo | Auto | Council` — Solo and Council enabled, Auto disabled ("Coming in Task 7"). Mode is remembered per project.
- **Composer (council mode):** chip showing the council ("3 models · Balanced", click to edit) and a live cost estimate ("≈ $0.02–0.05 · cap $0.50"). Over cap → confirm dialog ("Run anyway" / "Edit council").
- **Council reply layout:**
  - Header: "Council · 3 members · $0.041 · 21 s · confidence: medium".
  - **Final answer** first (markdown, copy, save-to-memory).
  - **Disagreement panel** (collapsible, open by default when contradictions exist): *Agreed* · *Disagreed* (each topic with every member's stance, model + lab badge; "needs evidence" tag) · *Only one model raised* · *Blind spots*. Each item has "Save to memory" (e.g. a contradiction → a `question` record).
  - **Members:** side-by-side collapsible cards on wide screens, tabs on narrow; each streams live and shows model, lab badge, status (streaming / done / failed / substituted), tokens, cost, latency.
- **Settings → Council tab** (per project): preset picker, member list (add via model picker, remove, reorder; 3–10), synthesizer picker, max output tokens per member, budget cap, timeout.

- **Playwright:**
  1. Switch to Council → estimate visible → send → three member cards stream → final answer + disagreement panel render with a contradiction marked "needs evidence".
