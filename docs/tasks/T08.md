**Goal:** hypotheses get **tested, not just argued**. A hypothesis becomes an experiment with **predictions locked before anything runs**; the app writes Cursor instructions; the owner runs them in Cursor; the app reads the repo (read-only) and decides **supported / refuted / inconclusive deterministically** from the results file. **The app never executes code.**

## 1. Data model (project DB, new migration)
- `experiments`: id (`E-n`), linked hypothesis ids, title, objective, protocol steps (markdown), baselines, dataset/inputs, required runs (repeats) + seeds, environment notes, **predictions** (JSON list), **results contract** (expected file path + JSON schema), status, version, `locked_at`, `lock_hash`, verdict, verdict evidence (JSON), created_at/updated_at.
- **Prediction spec** (machine-checkable, zod): `{ id, metric, comparator: ">"|">="|"<"|"<="|"=="|"between"|"improves_over", value?, tolerance?, low?, high?, baseline?: { metric }, minImprovementPct?, aggregate: "mean"|"median"|"all_runs"|"any_run" }`.
- **Statuses:** `draft → locked → awaiting_run → checking → supported | refuted | inconclusive`, plus `replicated` when the replication rule passes.
- **Preregistration lock:** locking stores a SHA-256 over the canonical JSON of objective + protocol + predictions + contract, plus the repo HEAD at lock time. Locked experiments are immutable; editing creates **version n+1** (status back to draft) and the UI shows "modified after lock" history.

## 2. Design flow
- From a hypothesis record (or a council `experiment_design` reply): **"Design experiment"** → the routed model/council (task type `experiment_design`) returns a draft in the structured spec above (zod, one repair retry) → editable form (predictions as rows) → **Lock predictions**.
- **"Generate Cursor instructions"** (only when locked) produces markdown, saved to `.research/experiments/<id>/instructions.md` and copyable, telling Cursor to:
  - implement the experiment under `experiments/<id>/` in the code repo, deterministic with the given seeds and repeats;
  - write `experiments/<id>/results.json` exactly matching the contract: `{ experimentId, lockHash, commit, runs: [{ seed, metrics: { … } }], env: { … }, notes }`;
  - commit with message `exp(<id>): <short description>` and never edit `.research/`.
- Also write the JSON Schema to `.research/experiments/<id>/results.schema.json`.

## 3. Check results (read-only, deterministic)
"**Check results**" uses the Task 5 read-only repo tools:
1. Find commits after `locked_at` whose message contains the experiment id; read `results.json` at HEAD (size limit 2 MB; treat as untrusted).
2. Validate against the schema; `lockHash` must match; flag commits dated before the lock.
3. **Evaluate each prediction in code** (not by an LLM) over the runs using its aggregate; require the declared number of runs.
4. **Verdict rules:** all predictions pass → `supported`; any prediction clearly fails → `refuted`; missing runs/metrics, schema errors, lock mismatch or too few runs → `inconclusive` with the specific reason.
5. Then a strong model (routed as `results_interpretation`) writes an **interpretation note**: plausible confounds, threats to validity, next steps. **It cannot change the verdict.** It may raise a concern flag, shown next to the verdict.
6. The user may **override** a verdict only with a written reason (logged with timestamp).
- Store verdict evidence: commit SHA, file path, per-prediction observed value vs expected, pass/fail.

## 4. Hypotheses and memory
- The verdict updates the linked hypothesis status (`supported`/`refuted`/`inconclusive`). This loop and the user are the **only** ways to set those statuses (the scribe rule from Task 6 stays).
- Refuted and inconclusive results stay in memory as **"tried"** knowledge: the context package (Task 6) includes a compact "Already tested" section whenever related hypotheses come up, so the team doesn't propose them again unknowingly.
- **Replication:** "Request replication" generates new instructions (new seeds, optionally another dataset); `replicated` = ≥ 2 independent locked runs that pass.

## 5. Research timeline
A **Timeline** view (and memory-panel tab): hypotheses → experiments (versions) → runs → verdicts → replications, in time order, with filters by status; click through to records, commits and reports. Write a per-experiment `report.md` into `.research/experiments/<id>/` and include verdicts in `memory.md`.

## 6. Tests
- **Vitest:** every comparator and aggregate (incl. tolerance, `between`, `improves_over` with `minImprovementPct`); canonical lock hash stability and versioning on edit; schema validation of results; lock-hash mismatch and pre-lock commit flags → inconclusive; too few runs → inconclusive; interpretation step cannot alter the verdict; hypothesis status transitions only via loop/user; override requires a reason; replication rule; the 2 MB limit; seed uniqueness/no-overlap (from §0).
- **Playwright** with a temp git repo (the test itself writes `results.json` and commits, simulating Cursor):
  1. Hypothesis → Design experiment → edit a prediction → Lock → instructions generated and saved.
  2. Passing results committed → Check → **supported**, hypothesis updated, timeline shows it.
  3. Failing results → **refuted**; the "Already tested" note appears in the next related chat's context indicator.
  4. Missing file → inconclusive with a clear reason.
  5. Override requires a reason; edit after lock creates version 2.
