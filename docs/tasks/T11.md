## 1. Literature retrieval — top priority (LitSearch R@5 10%, R@20 16%)
Finding the right papers is the product's core promise; this is far too low. Improve `search_papers` in stages and measure each stage with `pnpm eval:litsearch --limit 100` (report R@5/R@20 per stage):
1. **Baseline** as today.
2. **Query expansion:** an LLM (default model from `config/defaults.json`) turns the question into 3–5 diverse queries (keywords, technical synonyms, likely method names); run all; merge.
3. **Semantic reranking** of the merged candidates (title + abstract) with the local Qwen3 embedder using the query instruction; keep RRF as a fallback.
4. **Citation hop:** for the top 5 candidates, pull references/citations (OpenAlex/S2) and rerank the expanded pool.
5. **LLM rerank** of the top 30 (cheap model, structured scores) — keep only if it helps per the numbers.
Ship the best stage combination as the default (cost and latency per query reported). **Target: R@5 ≥ 35%, R@20 ≥ 55%** (published LitSearch results put commercial search engines at ≤ 42.8% R@5). If not reached, report the best and what's limiting it.

## Addendum 2 — ranking (lead)

Pool recall is ~98%, so **ranking** is the lever. Speed up and focus:

1. Before Qwen rerank, cut the pool to the **top 150 by RRF**; embed title+abstract in batches; **cache candidate embeddings** across queries and stages.
2. Then **LLM-rerank the top 50** (cheap fast model, structured scores) and compare: **RRF only vs Qwen vs Qwen + LLM**.
3. **Per-query timeout (90 s)** so one stuck query can't hang the run; count timeouts in the report.
4. Use **`--limit 50`** for each stage comparison, then confirm the winner on all 100.

Shipped default must stay under **~20 s** per search.
