# Task 6 — Scribe, semantic memory and context assembly

Repo: `heyronith/araitchi` (Task 5b done at `ddd820d`). Read `AGENTS.md`, `docs/STATUS.md`, `docs/ARCHITECTURE.md` first. Save these instructions as `docs/tasks/T06.md`.

**Goal:** the team remembers. After each reply a cheap **scribe** model files durable research facts into the project notebook; every request gets a **context package** of the most relevant memory; models can **search memory** with tools. **Done when:** a fact established in yesterday's chat is used in a new chat without being re-pasted. **Out of scope:** routing (Task 7), validation loop (Task 8).

---

## 1. Local embeddings (bundled — no Ollama, no external server)
- Use `@huggingface/transformers` (Transformers.js, ONNX) on the **server only**.
- **Default model (quality): `Qwen3-Embedding-0.6B`** via its ONNX/Transformers.js port (Apache 2.0, 1024-dim, 32K context, instruction-aware — use the documented query instruction for queries, none for documents). Use the 8-bit quantized ONNX weights (~0.6 GB). Pin the model revision.
- **Light alternative (setting `memory.embeddingModel`):** `Xenova/all-MiniLM-L6-v2` (~25 MB, 384-dim) for low-memory machines. Switching models triggers a full re-index (vectors are stored with their model id; never mix models in one search).
- If the chosen Qwen3 ONNX port does not load in Node on macOS arm64 or Windows x64, fall back to `onnx-community/embeddinggemma-300m-ONNX`, and report which model you shipped and why.
- **Packaging:** not committed to git. Downloaded once on first use into `<dataDir>/models/` (set Transformers.js cache dir), with progress shown in the UI ("Preparing local memory model… 610 MB, one-time"). Works offline afterwards. If the download fails, memory search falls back to keyword (FTS) only and the UI says so.
- Run the embedder in a **`worker_threads` worker** so it never blocks request handling. Batch inputs.
- Add `@huggingface/transformers` and `onnxruntime-node` to `serverExternalPackages`. Must work on macOS (arm64 + x64) and Windows x64.
- Code against an `Embedder` interface so tests use a deterministic fake embedder.

## 2. Vector index (per project, no native SQLite extensions)
- Table `embeddings(owner_type: record|session_summary|doc_chunk|paper, owner_id, chunk_idx, text_hash, model, vector BLOB float32, updated_at)`.
- Brute-force cosine similarity in JS (projects are small). Re-embed only when `text_hash` changes. Document the expected scale limit (~50k chunks) in ARCHITECTURE.
- Index: records (title + body), session summaries, library document chunks (~800-char chunks with page numbers), saved papers (title + abstract).
- **Hybrid search:** FTS5 BM25 + vector cosine combined with reciprocal-rank fusion; small boosts for pinned and recent; filters by type/status. `read_document` (Task 5) now uses hybrid ranking instead of keyword-only.
- **Backfill:** on opening a project after upgrade, index existing content in the background with progress; "Rebuild memory index" button in the memory panel.

## 3. Scribe
- Runs **asynchronously after every completed assistant reply** (solo or council final answer); never blocks or delays the reply.
- Model: setting `scribe.model`. **Default = the project's council synthesizer model** (a strong frontier model) — the scribe decides what the team remembers, so quality comes before cost. The user may pick a cheaper model in Settings; show the measured per-reply scribe cost next to the picker. `scribe.enabled` (default on); `scribe.requireReview` (default **off**).
- **Scribe quality eval** (`pnpm eval:scribe`, manual, uses the real OpenRouter key): 20 fixture transcripts in `evals/scribe/` with expected records (type, key title terms, status). Scores precision, recall, duplicate rate and invented-content rate per model, plus cost per reply. Run it for the default model and two cheaper candidates and include the table in your report.
- Input: last user message, the reply (wrapped as untrusted data), the council analysis if any, and a compact list of existing active records (id, type, title, status) to avoid duplicates. Prompt in `src/lib/server/prompts/scribe.md`: extract only **durable research content** (hypotheses, experiment plans/results, decisions with reasons, papers referenced, open questions, key facts as notes); ignore chit-chat; never invent; prefer updating an existing record over creating a duplicate.
- Output (zod-validated JSON, one repair retry):
  ```
  { create: { type, title, body, status?, tags? }[]  (max 5),
    update: { id, status?, appendBody? }[]           (max 5) }
  ```
- **Dedupe:** before creating, if an existing record of the same type has cosine ≥ 0.90, convert to an update or skip.
- Records get `source` = the model that produced the content (council: the synthesizer, or the member if the item came from a specific member) and a new column `created_by` = `scribe|user`.
- **Never deletes.** Status changes on hypotheses are allowed only as `proposed → testing` from chat content; `supported/refuted` are reserved for the validation loop (Task 8) or the user.
- UI: a compact line under the reply: "Memory: +2 hypotheses · 1 question updated" (click → highlights them in the panel), with **Undo** (reverts that scribe batch). Records show an "Added by scribe" badge. If `requireReview` is on, items arrive as suggestions with Accept / Dismiss.
- Log scribe cost in usage tracking; show it in the reply footer as "+ memory $0.0002".

## 4. Session summaries
Per chat, maintain a rolling summary (≤ 300 words) updated by the scribe every 6 messages and when a chat is left idle; stored in `session_summaries` and written at the top of the chat's `sessions/*.md` transcript.

## 5. Context package (replaces Task 3's simple brief + pinned)
- Built **once per request** and shared by solo and every council member. Budget setting `context.memoryTokens` (default 6,000).
- Order: brief (cap) → pinned records → active hypotheses (`proposed|testing`, titles + one line) → top-K hybrid results for the current user message (records, session summaries from **other** chats, document chunks, papers), deduplicated, until the budget is used.
- Each item labeled with a short reference id (e.g. `[H-12]`, `[D-3]`, `[P-7]`) that models are told to cite; the UI renders those references as clickable chips that open the record.
- **Context indicator** above the composer: "Context: brief · 3 pinned · 5 relevant (1.8k tokens)" — expandable to show exactly what was included.
- Memory items are wrapped as project data (trusted from the user's own notebook, but content originating from tools stays marked untrusted).

## 6. Memory tools for models (read-only, through the broker)
`search_memory({ query, types?, limit≤20 })`, `get_record({ id })`, `list_hypotheses({ status? })`, `list_experiments({ status? })`, `search_library({ query })`. New composer toggle **Memory** (default on).

## 7. Tests
- **Vitest:** fake embedder determinism; vector + FTS RRF ranking; re-embed only on text change; dedupe threshold converts create → update; scribe JSON validation, caps (≤ 5), repair path, disabled setting, no deletes, status-change restrictions; undo reverts a batch; context builder respects the token budget and always includes brief + pinned; reference-id rendering; memory tools; worker embedder interface (with fake); fallback to FTS when embedder unavailable.
- **Playwright** (mock scribe returns scripted JSON):
  1. Chat A: state a fact → "Memory: +1 note" line appears → record visible with "Added by scribe".
  2. New chat B: ask a related question → mock model's received payload contains that record in the context package; context indicator lists it.
  3. Undo removes the scribe batch.
  4. `requireReview` on → suggestion appears → Accept creates the record.
  5. Rebuild index shows progress and completes.
- Optional real-embedding integration test, skipped unless `ARAITCHI_REAL_EMBEDDINGS=1` (run once locally and report the result).
